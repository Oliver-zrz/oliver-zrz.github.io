换一台电脑，最麻烦的往往不是重新装编辑器，而是那些已经调顺手的东西散在各处：常用 Skill、给 Agent 的约定、环境配置、排过一次却没有留下记录的问题。

我希望把这些东西收在一个地方。做完一项工作，不只留下代码，也留下当时为什么这样判断、怎样确认结果。值得分享的部分，再整理成一篇读得懂的文章。

这次我把它做成了一个私有工作仓库和一个公开博客仓库。

## 两个仓库，各自保存什么

私有的 `dev-home` 保存完整的用户 Skill、Agent 约定、环境说明和工作底稿。公开的博客仓库保存网站源码、整理好的文章和列明的配图。

这样安排有一个很实际的好处：记录时可以保留足够的上下文，发表时又能逐篇选择内容。原始日志不需要为了方便写文章而整个搬进公开仓库。

图里有两条路径。上面一条把真实工作整理成文章，下面一条把已经整理好的开发能力恢复到另一台电脑。它们共享一个私有来源，但交付的内容不同。

## 每项工作都有一个明确位置

工作目录按日期和任务建立，例如：

```text
work/2026/2026-11-25-personal-dev-home/
  work.json
  record.md
  assets/
  raw/
```

`record.md` 写目标、关键决策、实际改动、验证证据和还没解决的问题。`work.json` 记录类型、状态和关联文章。需要保留的图放进 `assets/`；大体积或敏感原始日志放进被 Git 忽略的 `raw/`。

同一个问题的后续追问继续更新原记录。目录按任务组织，技术主题交给标签表达，不用在“性能”“图模式”“某个项目”之间反复决定一份记录应该放在哪里。

记录不需要很长。一次失败尝试如果能解释为什么排除了某条路线，就值得留下；重复的终端输出通常没有必要完整抄录。

## 迁移先做到可核对、可恢复

Skill 完整源文件和 SHA-256 校验和一起存放。恢复前先核验来源文件，再比较目标电脑上的内容：相同的跳过，缺失的复制，不同的先备份。

Windows 和 Linux/macOS 分别有一个启动脚本，底层共用 Python 标准库工具。已经准备好 Git 和 Python、并登录私有仓库账号后，就可以克隆仓库并运行恢复入口。

恢复范围包括用户 Skill、个人 Agent 日志约定和本机仓库指针。机器上额外安装的 Skill 不会被删除，原有全局约定会保留。少量 Codex 偏好单独导出成示例配置，供合并使用。

这还不等于复制整台电脑。GitHub 登录态、SSH 密钥、NPU 驱动和硬件环境各有自己的生命周期，需要在目标机器上准备。环境说明负责把这些前提讲清楚，不能把“已经复制了 Skill”写成“运行环境已经通过验证”。

## 从工作底稿到一篇文章

文章放在 `blog/posts/<slug>/`，正文用 Markdown，元数据和允许公开的图片清单放在 `post.json`。

我给这一过程留了三个分工：`work-journal` 负责找到工作记录并组织材料，`shuorenhua` 负责清理套话和理顺表达，`diagram-design` 负责用图解释关系、流程或变化。

文章围绕一个具体问题写。读者需要知道：问题是什么，观察到了什么，为什么采用这条路径，怎样验证，以及结论到哪里为止。标题不必每篇一样，素材不足时也不硬凑“完整复盘”。

写图也一样。架构和数据流适合画图，几个属性的对照可能用表格更清楚。图应当解释正文，不能只是填满版面。

## 同步只处理选定的公开内容

导出工具只读取标为 `public` 的文章，以及该文章逐个列明的配图。正文和图片从私有仓库导出，公开仓库里的文章保持为同一来源的镜像，避免两边各改一份。

网站使用 Astro 构建，提供文章目录、关键词搜索、标签筛选、工具箱、RSS 和明暗主题。提交公开仓库后，GitHub Actions 构建静态文件，由 GitHub Pages 承载。

私有工作目录不会作为网站构建输入。导出过程还会拒绝明显的凭据内容、未列入清单的相对图片和越界文件路径。这些检查帮助减少误操作，文章是否适合公开，仍要结合内容本身判断。

## 怎样确认这套流程能用

迁移与导出的测试覆盖了几个会真正影响使用的行为：重复恢复不再改文件、已有约定保留、不同内容先备份、校验失败时不安装、草稿不公开，以及没有列明的图片不能跟着导出。

这些测试通过，说明对应的工具行为经过了检查；它们不能证明每个 Skill 都已经在 NPU 上运行过，也不能证明任何一篇文章都没有事实错误。硬件验证和文章审阅仍然各自完成。

还有一个边界：给 Agent 写下工作约定，不等于安装了能观察所有程序的后台记录器。遵守约定的 Codex 会话可以在实质工作结束时留下一份记录；其他工具的工作，需要通过同一个入口补进来。

我希望这套结构能随着实际使用慢慢长起来：工具有来源，工作有目录，结论有证据，文章有一个稳定的公开地址。
