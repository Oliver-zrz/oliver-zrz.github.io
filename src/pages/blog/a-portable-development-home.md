换电脑时，编辑器容易重装，调顺手的工作环境却不容易带走。常用 Skill、给 Agent 的约定、零散的环境配置，往往各放一处。至于排过的问题，如果当时没记，下次还得重新找。

我想把这些东西收拢起来。配置能恢复，工作有记录；以后换一台电脑，可以接着做，也能翻到自己当时为什么这样改。

于是有了两个仓库：一个留工作底稿，一个放公开文章。

## 两个仓库

私有的 `dev-home` 保存完整的用户 Skill、Agent 约定、环境说明和工作底稿。公开的博客仓库保存网站源码、整理好的文章和列明的配图。

记录时，先把事情记完整；发表时，再选值得分享的部分。原始日志留在工作区，网站只接收整理好的文章。

## 先给记录找个位置

工作目录按日期和任务建立，例如：

```text
work/2026/2026-11-25-personal-dev-home/
  work.json
  record.md
  assets/
  raw/
```

`record.md` 写目标、关键决策、实际改动、验证证据和还没解决的问题。`work.json` 记录类型、状态和关联文章。需要保留的图放进 `assets/`；大体积或敏感原始日志放进被 Git 忽略的 `raw/`。

同一个问题继续写在原记录里，技术主题用标签区分。这样不用在“性能”“图模式”和项目名之间反复纠结该放哪份目录。

一次失败尝试如果解释了为什么排除某条路线，就值得记。重复的终端输出，摘出能支撑判断的几行就够了。

## 克隆之后，怎样恢复

Skill 完整源文件和 SHA-256 校验和一起存放。恢复前先核验来源文件，再比较目标电脑上的内容：相同的跳过，缺失的复制，不同的先备份。

Windows 和 Linux/macOS 分别有一个启动脚本，底层共用 Python 标准库工具。已经准备好 Git 和 Python、并登录私有仓库账号后，就可以克隆仓库并运行恢复入口。

恢复范围包括用户 Skill、个人 Agent 日志约定和本机仓库指针。机器上额外安装的 Skill 不会被删除，原有全局约定会保留。少量 Codex 偏好单独导出成示例配置，供合并使用。

GitHub 登录、SSH 密钥、NPU 驱动和硬件依赖，需要在新电脑上另外准备。恢复脚本复制的是 Skill 和配置；NPU 程序能不能运行，还要在目标环境里检查。

脚本结束后，`python tools/devhome.py doctor` 可以检查仓库指针、日志 Skill 和全局约定是否恢复到位。Windows 运行 `bootstrap.ps1`，Linux/macOS 运行 `bash bootstrap.sh`，都会执行这一步检查。

## 从工作底稿到一篇文章

文章放在 `blog/posts/<slug>/`，正文用 Markdown，元数据和允许公开的图片清单放在 `post.json`。

先从记录里挑出一个问题，再把相关的尝试、改动和验证串起来。复杂的关系配张图，几项属性的比较用表格，文字能说清的地方就直接写。

读者需要能跟上当时的判断：观察到了什么，为什么改这里，结果怎样，还有哪里没验证。材料只够说明一个小问题，就写短一点。

## 选好内容，再发布

导出工具只读取标为 `public` 的文章，以及该文章逐个列明的配图。正文和图片从私有仓库导出，公开仓库里的文章保持为同一来源的镜像，避免两边各改一份。

网站使用 Astro 构建，提供文章目录、关键词搜索、标签筛选、工具箱、RSS 和明暗主题。提交公开仓库后，GitHub Actions 构建静态文件，由 GitHub Pages 承载。

私有工作目录不参与网站构建。导出时会检查明显的凭据内容、未列入清单的相对图片和越界路径；发布前仍要读一遍文章，确认里面的细节适合公开。

## 在另一套系统上跑一遍

迁移与导出的测试覆盖了几个会真正影响使用的行为：重复恢复不再改文件、已有约定保留、不同内容先备份、校验失败时不安装、草稿不公开，以及没有列明的图片不能跟着导出。

这些用例检查恢复与导出工具。Skill 的 NPU 硬件验证、文章的事实核对，另外进行。

最初的 Windows/Linux 远端检查，找出了两个问题。

第一处是换行符。本机按文件原始字节计算校验和，但 Git 提交时可能把 CRLF 转成 LF。Linux 检出后，文件含义没有变，校验和却不再一致。解决方式是在 `.gitattributes` 中让 Skill 镜像保留原始字节，其他文本仍统一为 LF：

```text
* text=auto eol=lf
skills/user/** -text
```

修复后，直接检查 Git 中实际提交的内容：初版快照的 130 个 Skill 文件，字节校验和全部与清单一致。另一台电脑拿到的是这个版本，只检查当前工作目录还不够。

第二处是 Windows 的 8.3 短路径别名。临时目录的短名称和展开后的长名称可能指向同一位置，却让字符串式的相对路径计算失败。工具改为先用 `Path.resolve()` 统一路径，再做边界和相对位置判断，并加了一条针对真实短路径别名的恢复测试。

后来为了保持免费运行，私有仓库关闭了云端 Actions，校验和测试在本地执行。这次 Windows/Linux 的运行结果，保留为当时版本的验证记录。

日常使用时，Codex 按工作约定在任务结束后写本地记录。上传私有仓库、整理草稿和发布网站，需要分别发出指令。这套约定不会在后台观察其他程序；在别处完成的工作，仍要补进记录。

眼下先把这几步做顺：做完的事有处查，换电脑时有处取，想分享时也有稿可写。
