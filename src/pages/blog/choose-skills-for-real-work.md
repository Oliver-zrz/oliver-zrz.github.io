我拿到过一份包含 400 个 Skill 的本地全景图。它按算子开发、模型部署、性能分析、精度调试、环境工具和写作画图等场景组织，看起来像一整间工具库。

真正开始整理时，我先看自己已经有什么，再去找当前工作缺少的能力。当时已有两个与 PyTorch/NPU 测试相关的自建 Skill：一个生成 PTA API 功能用例，一个跟踪社区 PR 测试。

围绕这些工作，最直接的补充是环境检查、算子报错与精度定位、Profiling 分析、图模式参考和迁移流程。

## 清单是线索，源码才是安装依据

全景图里的名称和介绍能帮助缩小范围，安装前还需要确认目录真的存在，入口引用的脚本、参考文件和子 Skill 是否齐全。

这次选择来自三个公开仓库：Ascend 官方的 `agent-skills`、CANNBot，以及 `awesome-ascend-skills`。下载后固定在具体提交上，保留所选目录、参考文档、脚本和许可证，再做结构与文件检查。

有一个图模式分诊入口引用了没有在该提交里找到的精度诊断子 Skill。这种情况下，只装入口会留下不完整的调用链，所以这一批先保留可独立使用的知识入口和模板。

## 最后装了哪些

![面向实际 NPU 开发工作的五类 Skill，包括环境检查、算子调试、图模式、性能分析和模型迁移](/media/choose-skills-for-real-work/skill-map.svg)

| 方向 | 数量 | 解决的问题 |
|---|---:|---|
| 设备与环境 | 4 | 设备状态、CANN 依赖、架构识别、HCCL 环境 |
| 算子调试与精度 | 3 | 返回码、plog、精度偏差和比较标准 |
| 图模式 | 2 | npugraph_ex 使用与最小示例 |
| 性能分析 | 5 | 计算、通信、Host 与 Roofline 分析 |
| PyTorch 到 NPU 迁移 | 4 | 迁移流程、环境、代码替换和接口查询 |

合计是 11 个顶层目录，包含 7 个配套子 Skill，共 18 份 `SKILL.md`。保留子 Skill 很重要：性能分析和迁移入口需要借助它们继续完成具体工作。

内部平台 CLI 没有可核验的公开安装源，课程考试工具与当前开发工作关系也不大，因此没有一并加入。生产部署和驱动安装则留到有明确目标环境时再处理。

## 安装检查说明了什么

18 份 Skill 入口通过了结构校验，61 处入口 Markdown 本地引用检查通过。附带的 18 份 Python 文件完成语法检查，其中一份是精度调试模板，按文档替换占位符后再检查。Roofline 脚本还运行了内置离线自检。

这些结果只能说明对应的文件、结构和离线行为经过检查。设备采集、编译、通信和迁移需要目标 Linux/NPU 环境，不能据此写成“所有能力已实测通过”。

为了适配 Codex 的入口格式，少数 Skill 的 `keywords` 从顶层移入 `metadata`，内容保留；没有为适配格式而改写上游技术流程。每个顶层目录附带来源记录和文件哈希，后续更新可以知道自己装的是哪一版。

## 工具之后，还需要把工作讲清楚

除了技术 Skill，我还整理了“说人话”和“技术图解”两个本地入口。前者用来减少重复铺垫、名词化和套话，同时保留数字、条件、责任主体和作者语气；后者根据问题选择架构图、流程图、时序图或其他表达方式。

例如，“单卡通过 8 项，跳过 2 项；多卡尚未运行”不能被润色成“所有测试通过”。同样，一张图为了排版更干净，也不能静默删掉一个异常分支。

选工具与写文章在这里有一个共同要求：交代清楚已经做了什么，以及还没确认什么。把这一点留下来，下一次遇到相似问题时，记录才真正有用。
